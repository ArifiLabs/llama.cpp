2. MEMORY TYPES, AND WHICH ARE ELIGIBLE AT ALL
---------------------------------------------------------------------------------------------------
  16 types are enumerated (0-7 mirrored as 8-15). But EVERY storage buffer this engine creates
  reports VkMemoryRequirements::memoryTypeBits = 0xf (source B, every `state=attempt` line, 46 of
  46). Only memory types 0,1,2,3 can therefore ever hold our weights. Types 4-15 - including every
  AMD DEVICE_COHERENT / DEVICE_UNCACHED variant - are enumeration noise for this workload.

  idx  heap  flags                                                        eligible (typeBits 0xf)
  ---  ----  -----------------------------------------------------------  -----------------------
    0     0  DEVICE_LOCAL                                                 YES
    1     1  HOST_VISIBLE | HOST_COHERENT                                 YES
    2     2  DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT                  YES
    3     1  HOST_VISIBLE | HOST_COHERENT | HOST_CACHED                   YES
    4     0  DEVICE_LOCAL | DEVICE_COHERENT_AMD | DEVICE_UNCACHED_AMD     no
    5     1  HOST_VISIBLE | HOST_COHERENT | DEVICE_COHERENT_AMD | DEVICE_UNCACHED_AMD    no
    6     2  DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT | DEVICE_COHERENT_AMD | ...     no
    7     1  HOST_VISIBLE | HOST_COHERENT | HOST_CACHED | DEVICE_COHERENT_AMD | ...      no
   8-15     exact mirrors of types 0-7                                    no

  VERDICT: BEYOND THE RESERVATION THERE ARE EXACTLY TWO USABLE MEMORY TYPES.
    type 1 - HOST_VISIBLE | HOST_COHERENT                (uncached / write-combined)
    type 3 - HOST_VISIBLE | HOST_COHERENT | HOST_CACHED  (snooped, CPU-cached)
  Both sit on heap 1. That is the whole lever this lane has, and it is a real one: type 3 is
  already in production use on this box for the transfer/staging buffers (7 allocations,
  27,695,584 B, source B), so the driver demonstrably serves it - it has simply never carried
  weights.

3. WHICH TYPE EACH BUFFER CLASS GETS TODAY - and WHY
---------------------------------------------------------------------------------------------------
  Aggregate over the whole S-X8 load (source B, 46 successful allocations):

  class                              allocs           bytes   memtype  heap  flags
  ---------------------------------  ------  --------------   -------  ----  --------------------------
  weights, device-local                  23  23,223,063,296         0     0  DEVICE_LOCAL
  weights, HOST SPLIT                     5   3,281,736,960         1     1  HOST_VISIBLE|HOST_COHERENT
  KV / small tensors                     11     196,109,596         2     2  DL|HOST_VISIBLE|HOST_COHERENT
  staging / transfer                      7      27,695,584         3     1  HV|HC|HOST_CACHED

  WHY the host split lands in type 1 - it is ENUMERATION ORDER, never a measurement:
  ggml_vk_placement_attempts() (ggml-vulkan.cpp, UMA branch) offers the required-flag passes
  { DEVICE_LOCAL|HOST_VISIBLE|HOST_COHERENT }, { DEVICE_LOCAL }, { HOST_VISIBLE|HOST_COHERENT }.
    pass 1 (DL|HV|HC) matches only types 2/6/10/14, all on the 256 MiB heap 2 -> structurally dead
           for GiB-sized weight blocks. (It is alive for the small KV tensors, which is exactly why
           those land in type 2.)
    pass 2 (DL) matches types 0/4/8/12 on heap 0 -> takes every block until heap 0 is full.
    pass 3 (HV|HC) matches types 1 and 3 on heap 1. ggml_vk_find_memory_properties() walks memory
           types in ASCENDING INDEX, and the planner deduplicates keeping the FIRST position, so
           type 1 beats type 3 purely because 1 < 3. Nothing measured it.

5. CORRECTNESS NOTE
---------------------------------------------------------------------------------------------------
  Every eligible heap-1 type (1 and 3) carries HOST_COHERENT. Moving the host split from type 1 to
  type 3 therefore needs no vkFlushMappedMemoryRanges / vkInvalidateMappedMemoryRanges code and
  adds no new coherence obligation - which is the real reason outputs stay bit-identical, a
  stronger argument than "placement does not change arithmetic".
